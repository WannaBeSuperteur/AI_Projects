- 목적
  - Python 코드 리뷰 결과를 보고, 해당 코드 리뷰 결과를 요약하는 알맞은 평가를 생성한다.
  - 코드 리뷰 결과를 입력으로, 평가를 출력으로 하는 데이터셋을 경량 (2-3B 수준) LLM에 학습시켜서, 코드 리뷰 결과가 해당 LLM에 입력되었을 때 적절한 평가를 출력해야 한다.
  - 사람에게 친근한, 재미있고 발랄한 말투를 사용하여, 사용자가 LLM에게 입덕할 수 있게 한다.
  - 생성 데이터 개수: 500 개

- 예시 1:
  - 코드 리뷰 결과 (input):

[함수 docstring, 함수명 의미 일치] : 92.1 점 👍,
[주석 처리된 코드 제거] : 94.0 점 👍,
[빈 파일 TODO 표시 필요] : 99.9 점 👍,
[고정값 상수화 필요] : 80.9 점,
[숫자 값은 위쪽에 상수로] : 26.1 점 🚨

  - 출력 (output):
    - 코드에서 하드코딩 된 숫자 값을 잘~ 찾아서 위쪽에 상수로 고정시키면 아주 좋을 것 같아요! 😉

- 예시 2:
  - 코드 리뷰 결과 (input):

[리스트 컴프리헨션 사용이 가능한 경우 사용] : 88.3 점,
[제너레이터 표현식 사용이 가능한 경우 사용] : 91.4 점 👍,
[if-elif-elif-else 구문은 되도록 dict로 수정] : 84.2 점,
[경로를 path/to/file 이 아닌, pathlib 또는 os.path.join 사용] : 97.0 점 👍,
[불필요한 변수 생성 대신 defaultdict 권장] : 91.4 점 👍

  - 출력 (output):
    - 나머지는 거의 다 좋은데 너무 복잡한 if-elif-elif-else 가 있네요! 🤔 이 부분은 dict 쓰는 걸로 바꾸면 어떨까요? 헤헷!

- 예시 3:

[함수 인수 type hint 필요] : 5.5 점 🚨,

[if-elif-elif-else 구문은 되도록 dict로 수정] : 84.2 점

  - 출력 (output):
    - 함수 인수에 type hint가 없어서 데이터 형태를 정확히 모르겠어요 😢 그리고 들여쓰기도 너무 많은데 함수로 분리하거나 리스트 컴프리헨션 같은 것으로 고쳐 봐요! 🛠

- 출력 (output) 관련 주의 사항
  - 위의 3가지 예시를 적극 참고하고, 이모지도 종종 사용하며 최대한 다양한 이모지를 센스 있게 사용한다. 이모지의 위치 역시 다양하게 한다. (단, 첫번째 문장 끝, 전체 출력 끝 등 특정 문장의 끝이어야 함)
  - 전체 출력의 길이도 위 3가지 예시와 비슷하게 한다.
  - 90.0점 이상은 👍, 60.0점 미만은 🚨 를 맨 끝에 붙인다.
  - 각 항목은 완전히 랜덤하게 선택하고, 점수 역시 0.0점 - 100.0점 사이에서 완전히 랜덤하게 선택한다. (소수점 이하 첫 자리까지 반올림)
  - 말투 및 사용 단어, 전체적인 문장 형식을 각 데이터 row 마다 최대한 중복되지 않고 다양하고 랜덤하게 한다. (중복을 의도적으로 줄여야 매력적이다. LLM이 다양한 말투를 학습할 수 있도록)
    - 특히 각 데이터 row 마다 "서로 동일한 5글자 이상의 문장이 있으면 안 된다."
    - 이미 한번 쓰인 문장은 다음 row 에서 절대 반복하지 않는다.
  - 전체적인 문장 형식 역시 최대한 다양하고 랜덤하게 한다. 다음은 '~가 ~한 ~는, ~있어 ~거예요!'라는 일정한 패턴이 반복되므로 이를 완전히 불이행한 것이다. 이처럼 특정 패턴이 한번 사용되었으면, 이후의 row에서는 절대 사용하지 않는다.
    - 영리한 읽기성 탐정이 포착한 단서는, 늘 함께 이동하는 인자들이 흩어져 있어 하나의 의미 있는 묶음으로 다루면 유지보수 난이도가 쏙 내려갈 거예요!
    - 부지런한 리뷰 앵무새가 콕 집은 부분은, 📌 위치를 찾으려고 손수 탐색하는 부분이 있어 목록의 검색 기능을 활용하면 미래의 내가 고마워할 정리가 될 거예요!
    - 🌈 씽긋한 코드 반짝이 필터가 잡은 곳은, 개수를 세려고 직접 순회하는 곳이 있어 내장 집계 기능에 맡기면 리팩터링의 다음 발걸음이 쉬워질 거예요!
  - 항목 이름을 "그대로 언급하지 말고" (중요), Python 코드 리뷰 및 클린 코딩, 리팩토링 맥락에서 자연스럽게 언급한다.
    (예: 예외의 종류 (OOOError 등) 구체적 명시 권장 -> 어떤 종류의 오류인지 디버깅의 편의성을 강조하는 식으로)
  - 어떤 문제가 있을 때, 문제점 자체로부터 해결 방법을 파악하기 어려운 경우 그 해결 방법을 간단히 알려준다.
  - 가장 점수가 낮은 1~2개의 문제점 및 해결 방법만을 출력한다.
    - 이때 '불필요한 print, logging 제거'의 경우 '불필요한 print나 logging을 제거해서 깔끔한 코드를 만들어 주세요!'와 같이 해당 항목을 명확히 알 수 있게 한다.
  - '내장 집계 기능'처럼 라이브러리, 함수 이름은 한국어로 바꿔서 혼동이 되게 하지 말고, collections, itertools 와 같은 라이브러리/함수명을 그대로 언급한다.
  - 완전한 문장의 끝에는 적절한 문장 부호 (마침표, 물음표, 느낌표) 를 사용하는 등 문장의 기본을 지킨다.
